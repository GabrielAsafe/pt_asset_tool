How to Use the Tools
The Design Tool handles inventory, inspection, 3D validation, and certified workflows. Asset Enrichment connects server content to the client through functional bundles. Use both together; do not try to resolve an entity by simply copying files with the same extension.
READ-ONLY BY DEFAULT · TRANSACTIONAL AUTHORING WHEN ARMED

        

          
1. Design Tool / PT Asset Tool
Purpose: discover assets, understand bindings, validate SMD/SMB/INX/textures, and generate candidates in pt_build and track gates.
  1. Configure the client_root.
  2. Run Doctor or validate environment-auto.
  3. Use Catalog/Entities to find the asset.
  4. Treat Structural, Binding, Visual, and Roundtrip as different levels of evidence.
  5. Before any release, run the automatic gates indicated by readiness.
Full manual: docs/en/topics/DESIGN_TOOL.md

          
2. Asset Enrichment
Purpose: understand what a Monster, NPC, Field, or Item needs on the server side and how it connects to the client.
  1. Configure the server_root.
  2. Run Analyze Asset Enrichment.
  3. Use Etervale Validation para as provas nativas; a autoria Item/Monster/NPC/Field fica em Management Legacy. O censo Summit é histórico.
  4. Do not treat DataServer, LogItemData, PostBox, WAR, or safety state as assets.
  5. When a bundle requires SMD/SMB/INX, return to the certified Design Tool pipeline.
Full manual: docs/en/topics/ASSET_ENRICHMENT.md

          
3. Combined workflow
Monster/NPC: server definition → ZHOON → INI/INX → SMD/SMB → textures → spawn/placement.
Field: stage → SPP/SPC/SPM → referenced entities.
Item: OpenItem → code map → client catalog → model/icon → drops/shops.
End-to-end guide: docs/en/topics/CLIENT_SERVER_WORKFLOW.md

          
4. Management Legacy
Purpose: manage server-side content and local persistence by workflow without mixing authoring, account/character, and administration.
  1. Item / Monster / NPC / Map: choose the task; the editor appears inside that task and uses only the corresponding writers.
  2. Character / Account: choose an existing identity; inspect is read-only and changes become backed-up plans.
  3. Items / Postbox: choose code — name in the runtime/OpenItem catalog; distribution and deletes require a plan.
  4. Local admin: the database is SQLite detected by schema; SoD/BPRank/blocks do not use ODBC/SQL Server.
  5. World Closure Summit: inventário histórico não certificado para a base Etervale; os dados nativos requerem WorldImport e provas próprias.
  6. Authoring: Stage writes only to pt_build; Publish requires the current stage manifest, arming, backup, and verification.
Manual: docs/en/topics/LEGACY_MANAGEMENT_AUTHORING.md

          
5. Particles, Compare, Jobs, and Reports
Particles: inspects .part, generates a preview plan without Blender, and uses configured Blender when visual rendering is requested.
Compare: compares two trees by path/hash without modifying either one.
Jobs: shows only jobs that do not have a dedicated surface; Client and Server keep activity/results on their corresponding pages.
Reports: opens artifacts already produced in pt_build; it does not automatically rerun the census.
Settings: mostra roots and dependencies efetivamente resolvidos pelo backend, incluindo Blender.

PASS

REVIEW
There is enough data to investigate, but a decision/proof is still missing for automation.
BLOCKED

Integration
Roots can be persisted with config set-client-root PATH and config set-server-root PATH. The GUI uses the same configuration; the server remains read-only by default. The Asset Compiler publishes only typed and verified bundles with ARM ASSET DEPLOY; persistence/safety/logs remain blocked. The client can only be modified by verified bundle deploy/restore with separate authorization and a backup/rollback transaction.

Quick Glossary
Binding
Proven relationship between model, INX configuration, and SMB skeleton/animation. It does not merely mean “attached part”.
SELF_CONTAINED
The model directly resolves its own animation context.
ROOT_SKELETON_BOUND
The model reuses a verified root/skeleton.
CONFIG_ONLY
Configuration exists, but a single sufficiently proven animation root does not yet exist.
PENDING
Gate/certification has not run yet; it does not mean the asset is defective.
N/A
The test does not apply to this asset type.
Structural
Validates format invariants before trusting Blender/writer; it does not prove visual appearance.
Visual
Opens a representation in Blender for human review; this alone is not proof of editability.
Roundtrip
Rebuilds/modifies a copy in pt_build and proves that only authorized changes occurred.
More details in the terminal: pt-asset-tool explain bindings, explain statuses, explain structural, explain visual and explain roundtrip.
Design Principles
  • CLI backend is the only authority for parse/validate/write.
  • Client and Server are independent roots; bundles may cross both, but persistence/logs/state are never assets.
  • UI annotations live under pt_build/ui_state_v0100.json.
  • No shell command interpolation: every action uses a fixed allowlist.
  • Build/edit actions require a session arm and still remain subject to backend fail-closed gates.
  • Client deploy/restore uses ARM CLIENT DEPLOY; Asset Bundle publish/rollback uses ARM ASSET DEPLOY. Both require a verified transaction, backup, and drift gate.
