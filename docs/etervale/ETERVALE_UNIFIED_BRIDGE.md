# Etervale unified source integration — bridge v1

This integration **does not migrate the game engine to glTF**. It binds the Asset Tool to one Etervale checkout and delegates *native parsing* and *GLB export* to existing C# tools. The Asset Tool's old C++ source-contract scanner and the Summit data-pack compilers remain isolated from Etervale C# source authority.

## Setup on Gabriel's workstation

Run these commands from `~/Transferências/pt_asset_tool` after applying the second patch:

```sh
python3 app/pt_asset.py config set-etervale-root "$HOME/Transferências/Etervale-git"
python3 app/pt_asset.py config show
python3 app/pt_asset.py etervale status
python3 app/pt_asset.py etervale source-audit
```

`config set-etervale-root` validates `PristonTale.sln`, `assets/`, `Client/`, `Server/`, `Shared/` and `tools/PristonTale.AssetDump/*.csproj`. It saves `etervale_root` to the Asset Tool's normal machine-local application config; the old `client_root` and `server_root` fields are retained only for rollback.

| Role | Derived path | Note |
| --- | --- | --- |
| Game asset root (client *assets*) | `Etervale-git/assets/` | Do **not** use `Client/`; that folder holds C# source |
| Legacy server *data* root | `Etervale-git/assets/GameServer/` | Do **not** use `Server/`; that folder holds C# source |
| Active C# source checkout | `Etervale-git/` | Dedicated C# textual audit, separate from old C++ scanner |
| C# tools | `Etervale-git/tools/` | C# projects remain in the Etervale repo |
| Private data-type staging | Asset Tool `app/pt_build/` | No implicit game asset publication |

The GUI's existing asset resolver/registry can use the configured `assets/` client data root through `app_config.resolve_client_root`, and the legacy server modules can discover `assets/GameServer/`. **This does not certify each legacy screen against the new C# runtime**. The UI redesign remains a separate phase. In unified mode the old C/C++ `source_catalog` does **not** automatically reuse persisted Summit C++ source roots. Only explicit overrides can request those historical audits.

`PT_ETERVALE_ROOT` can override the persisted game root for one process. Explicit `PT_CLIENT_ROOT` / `PT_SERVER_ROOT` overrides still take precedence in legacy commands. To return to old persisted roots use `python3 app/pt_asset.py config clear-etervale-root`.

## Source audit (C#)

```sh
python3 app/pt_asset.py etervale source-audit
python3 app/pt_asset.py etervale source-audit --report csharp_audit_01.json
```

This enumerates `.cs` files and counts selected textual markers in `Client/`, `Server/`, `Shared/`, `Persistence/`, and `tools/`. It excludes `bin`, `obj`, `.git` and similar generated/vendor directories. **Text occurrences are not automatically evidence of runtime reachability:** comments, inactive code and test-only references can be included. Do not use this census for deletion, quarantine or authoritative dependency closure.

## Validate a real game asset through Etervale's parser

Dry-run only:

```sh
python3 app/pt_asset.py etervale validate --asset 'Field/Ricarten/village-2.smd'
```

Build and execute the C# reader (requires .NET SDK installed and restorable project dependencies):

```sh
python3 app/pt_asset.py etervale validate \
  --asset 'Field/Ricarten/village-2.smd' --execute --build
```

Only `assets/`-relative `.smd`, `.smb`, `.inx`, `.bmp` and `.tga` inputs are accepted. A candidate generated by the Asset Tool's writers may be validated by passing its **absolute** path via `--candidate`, provided the resolved path stays within the Asset Tool's `app/pt_build/` or historical root `pt_build/`. The inspector reads it without updating the game. For every executed validation, the wrapper verifies source SHA-256 before/after and writes a JSON report under `app/pt_build/etervale/validation/`.

This proves **reader acceptance** only, not geometry parity, skinning quality, correct gameplay timing or visual correctness.

## Validate multiple staged results

Create a manifest inside Asset Tool's `app/pt_build/`, for example `app/pt_build/etervale_candidates.json`:

```json
{
  "format": "PT_ASSET_ETERVALE_CANDIDATE_BATCH_V1",
  "candidates": [
    "pt_asset_tool/example/model.smd",
    "pt_asset_tool/example/animations.inx"
  ]
}
```

Paths in the manifest are relative to the containing `pt_build/` (either `app/pt_build/` or historical root `pt_build/`), or absolute within either location. The bridge refuses a manifest outside that directory, rejects path escapes and rejects non-asset extensions. No directories are scanned implicitly. The maximum is 500 paths per batch.

```sh
python3 app/pt_asset.py etervale validate-batch \
  --manifest "$PWD/app/pt_build/etervale_candidates.json"
python3 app/pt_asset.py etervale validate-batch \
  --manifest "$PWD/app/pt_build/etervale_candidates.json" --execute --build
```

The C# tool is built once, and the wrapper records `READER_ACCEPTED`, `FAILED`, or `BLOCKED_BY_BUILD_FAILURE` per candidate. Reports go to private staging; no result is published to Etervale.

## Export GLB for Blender / review

```sh
python3 app/pt_asset.py etervale export-glb --asset 'Field/Ricarten/village-2.smd'
python3 app/pt_asset.py etervale export-glb \
  --asset 'Field/Ricarten/village-2.smd' --output glb/village-2.glb --execute --build
```

The exporter uses `tools/PristonTale.GltfExport` and checks that a produced GLB has a glTF v2 container header. Output is restricted to private Asset Tool staging `app/pt_build/etervale/` and existing files are **not overwritten**. An `.inx` actor export passes the game `assets/` root to the C# tool. The wrapper does not support arbitrary flags, glTF sidecar files or reverse GLB-to-SMD conversion.

A successful export means **the GLB container is structurally plausible and the exporter returned success**; it does **not** mean the game renders GLB natively.

## Current format responsibility and known gaps

| Domain | Etervale authority today | Asset Tool responsibility | Certification |
| --- | --- | --- | --- |
| Stage SMD 0.72/0.73 | Engine3D `PristonSmdReader`; Shared `StageCollisionReader` | Parse/write candidates; compare against C# AssetDump | Reader bridge ready; actual assets untested here |
| Model SMD 0.62 / skeleton SMB | Engine3D `PristonSmdReader` | SMD/SMB writers, rig and roundtrip | Reader bridge ready; runtime visuals untested |
| INX | Engine3D `PristonInxReader`; WorldImport motion extractor | Write/verify MotionInfo | Reader bridge ready; gameplay timing untested |
| BMP/TGA | Engine3D texture decoder | Upscale, material tools and overlay | Reader bridge ready; visual output untested |
| GLB/glTF | `PristonTale.GltfExport` **output**, not a native runtime loader | Staged export/viewing | Export-only |
| `.smap/.scfg/.sfld/.sres/...` | Not established as accepted by Etervale C# | Legacy Summit compilers, kept separate | Not certified for new game |
| GameServer CP949 text / Field definitions | `PristonTale.WorldImport` | Inspect/author legacy server data | Needs integration test with database copy |
| Effect/VFX | `PristonTale.VfxImport` | Particles and effect authoring | Requires runtime VFX checks |

`PristonTale.WorldImport`, `PristonTale.VfxImport`, `PristonTale.DataImport` and others stay in the game repository and are **not executed automatically**, because they can change databases or assets. A future publishing workflow must have explicit backup, plan and approval.

## Verification boundaries

- In this delivery, the new bridge passed tests with synthetic projects and a mock `dotnet` executable. Etervale C# file discovery and source scanning were also checked against the uploaded Etervale source snapshot (which did **not** include the actual `assets/` directory).
- This environment does not have the `dotnet` SDK or the user's actual physical assets. Only the user's workstation can run `--execute --build` against its complete checkout.
- Successful Python tests prove the integration plumbing, not the native C# readers or visual output. All game writes and runtime GLB loading remain out of scope.
