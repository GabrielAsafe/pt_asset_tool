Como usar as ferramentas

O Design Tool cuida do inventário, inspeção, validação 3D e workflows certificados. O Asset Enrichment conecta o conteúdo do servidor ao client por bundles funcionais. Use os dois juntos; não tente resolver uma entidade apenas copiando ficheiros com a mesma extensão.

CLIENT + SERVER, READ-ONLY POR PADRÃO

1. Design Tool / PT Asset Tool

Para quê: descobrir assets, entender bindings, validar SMD/SMB/INX/texturas, gerar candidates em pt_build e acompanhar gates.

  1. Configure o client_root.
  2. Rode Doctor ou validate environment-auto.
  3. Use Catálogo/Entidades para encontrar o asset.
  4. Leia Structural, Binding, Visual e Roundtrip como níveis de evidência diferentes.
  5. Antes de qualquer release, rode os gates automáticos indicados pela readiness.

Manual completo: docs/tematicos/GUIA_DESIGN_TOOL.md

2. Asset Enrichment

Para quê: enxergar o que um Monster, NPC, Field ou Item precisa no lado servidor e como isso se liga ao client.

  1. Configure o server_root.
  2. Rode Analisar Asset Enrichment.
  3. Use o Explorador de bundles para investigar REVIEW/BLOCKED.
  4. Não trate DataServer, LogItemData, PostBox, WAR ou estados de segurança como assets.
  5. Quando um bundle exigir SMD/SMB/INX, volte ao pipeline certificado do Design Tool.

Manual completo: docs/tematicos/GUIA_ASSET_ENRICHMENT.md

3. Fluxo combinado

Monster/NPC: definição server → ZHOON → INI/INX → SMD/SMB → texturas → spawn/placement.

Field: stage → SPP/SPC/SPM → entidades referenciadas.

Item: OpenItem → code map → catálogo client → modelo/icon → drops/shops.

Guia de ponta a ponta: docs/tematicos/GUIA_WORKFLOW_CLIENT_SERVER.md

Integração

As raízes podem ser persistidas com config set-client-root CAMINHO e config set-server-root CAMINHO. A GUI usa a mesma configuração; o server permanece read-only. O client só pode ser alterado por deploy/restauro de bundle verificado, com autorização separada e transação com backup/rollback.

Glossário rápido

Binding
Relação comprovada entre modelo, configuração INX e skeleton/animação SMB. Não significa apenas “peça anexada”.
SELF_CONTAINED
O próprio modelo resolve diretamente seu contexto de animação.
ROOT_SKELETON_BOUND
O modelo reutiliza um root/skeleton verificado.
CONFIG_ONLY
Há configuração, mas ainda não há root de animação único suficientemente provado.
PENDING
Gate/certificação ainda não executado; não significa asset defeituoso.
N/A
O teste não se aplica ao tipo de asset.
Estrutural
Valida invariantes do formato antes de confiar em Blender/writer; não prova aparência visual.
Visual
Abre uma representação no Blender para revisão humana; não é prova de edição por si só.
Roundtrip
Reconstrói/modifica uma cópia em pt_build e prova que somente alterações autorizadas ocorreram.

Mais detalhes no terminal: python3 pt_asset.py explain bindings, explain statuses, explain structural, explain visual e explain roundtrip.

Princípios de design

  • CLI backend is the only authority for parse/validate/write.
  • Client e Server são raízes independentes; bundles podem cruzar as duas, mas persistência/logs/estado nunca são assets.
  • UI annotations live under pt_build/ui_state_v0100.json.
  • No shell command interpolation: every action uses a fixed allowlist.
  • Build/edit actions require a session arm and still remain subject to backend fail-closed gates.
  • Client deploy/restore uses a separate one-shot ARM CLIENT DEPLOY authorization and only verified workspace bundles may write known tracked paths.
